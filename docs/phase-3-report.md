# Phase 3 report — Band, data binding, API

**สรุป: ผ่านเกณฑ์หลักแล้ว** — รายงานข้ามหลายหน้า การจัดกลุ่ม (ซ้อนได้หลายชั้น) และยอดรวม SQL HTTP API และแพ็กเกจ npm ใช้ได้
ที่ยังค้าง: Docker build (เครื่องนี้ไม่มี Docker daemon), Postgres/MySQL (รอเจ้าของเลือก), ตารางใน band ที่จัดกลุ่ม

> **อัปเดต 2026-10-17** — แก้ลำดับ band หน้าแรก, ฟังก์ชันจัดรูปแบบใน `{{ }}`, ยอดเงินทศนิยมตายตัว, กลุ่มซ้อน,
> timeout/คิวของ HTTP API ดูหัวข้อ 2.1

> **การเปลี่ยนเกณฑ์ (ตัดสินโดยเจ้าของโปรเจกต์):** เกณฑ์ "benchmark เทียบ Jasper" ถูกนำออกจาก Phase 3 แล้ว

### 2.1 รอบแก้ไข 2026-10-17

- **ลำดับ band หน้าแรกผิด** — engine วางหัวคอลัมน์ไว้ *เหนือ* หัวเรื่อง (ตัวอย่าง sales-by-category เห็นชัด) ขณะที่หน้าออกแบบ
  แสดงหัวเรื่องก่อน แก้เป็น หัวกระดาษ → หัวเรื่อง → หัวคอลัมน์ (เหมือน Jasper) ความจุของหน้าไม่เปลี่ยน
  เทสต์ `first_page_band_order_matches_designer` (ตรวจตำแหน่ง y จริง, mutation แล้วล้ม)
- **ตัวเลขในแถวไม่มีคั่นหลักพันแต่ยอดรวมมี** — เพิ่มฟังก์ชันใน `{{ }}`: `number(x[, ทศนิยม])`, `bahttext(x)`,
  `thaidate(x[, "short"])`, `thaidigits(x)` ซ้อนกันได้และซ้อนการรวมค่าได้ เช่น `{{ bahttext(sum(item.amount)) }}`
  (`crates/tr-core/src/expr.rs`) — หน้าออกแบบรู้จักฟังก์ชันเหล่านี้ (ป้าย + ตรวจฟิลด์ข้างใน + จับคู่ฟิลด์ใหม่ได้)
- **ยอดเงินใช้ f64** → เปลี่ยนเป็น `rust_decimal` (ตอบคำถามข้อ 4 ตามที่แนะนำไว้) 0.1+0.2 = 0.3 พอดี,
  1,234,567.89 × 10,000 แถวถูกทุกสตางค์, `bahttext(1.005)` = หนึ่งบาทหนึ่งสตางค์
- **กลุ่มซ้อน** — หัวกลุ่มหลายอันที่มี `groupBy` = ชั้นนอก → ใน; ท้ายกลุ่มจับคู่จากชั้นในออกมา หรือระบุ `groupBy` เอง
  (`Template::group_levels` ใช้ร่วมกันทั้งตรวจและจัดหน้า) หัวกลุ่มทุกชั้นไม่ค้างท้ายหน้า — designer มีปุ่ม "เพิ่มกลุ่มย่อย"
- **HTTP API** — `TR_RENDER_TIMEOUT_SECS` (ค่าเริ่มต้น 30 → 504) และ `TR_MAX_CONCURRENT_RENDERS` (ค่าเริ่มต้น = จำนวนแกน)
  งานที่หมดเวลายังถือช่องจนเรนเดอร์เสร็จจริง CPU จึงไม่ล้น
- **ตรวจการผูกข้อมูลฝั่ง engine** (`tr_core::check::check_bindings`) — `thaireport validate t.json data.json` และ
  `render` แจ้งฟิลด์ที่ไม่มีในข้อมูล (เดิมพิมพ์เป็นช่องว่างเงียบๆ)
- WASM ↔ native ยังได้ PDF ตรงกันทุกไบต์ (`wasm_native_pdf_parity_via_node`) · build designer และ addon ใหม่แล้ว

### การแก้ที่พบระหว่างทาง
- **การวัดความกว้างข้อความเพี้ยน (native เท่านั้น)** — cosmic-text บน native fallback ไปฟอนต์ Thonburi ของระบบ
  สำหรับอักขระที่ Sarabun ไม่มี ทำให้ข้อความจัดกึ่งกลางเพี้ยนราว 2pt เทียบ WASM แก้โดย `BundledOnlyFallback`
- **ตัวนับหน้าในพรีวิวเป็น 1 เสมอ** — นับ `/Type /Page` จากไบต์ PDF ที่ถูกบีบอัด แก้โดยให้ engine คืนจำนวนหน้าจาก layout
- **ตัวเลขรวมปัดผิด** — `format!` ของ Rust ปัดครึ่งเป็นเลขคู่ ใบเสร็จต้องปัดครึ่งขึ้น แก้ใน `format_number`
- **เทสต์ `preview-client` ค้าง** — `initThaireport` เป็น async จึงคืน promise คนละตัวทุกครั้ง แก้ให้คืน promise เดิม

## 3. การวัดผลที่มี (ไม่ใช่การเทียบ Jasper)

วัดด้วย `thaireport render` (release, macOS arm64, รันครั้งเดียว ไม่ได้ทำซ้ำหลายรอบ) ใช้ template รายงานกลุ่มเดียวกันทั้งสองขนาด
จำนวนหน้านับจาก `/Count` ของ PDF ที่ได้:

| ข้อมูล | เวลา (real) | หน่วยความจำสูงสุด (max RSS) | ขนาด PDF |
|---|---|---|---|
| 300 แถว, 12 กลุ่ม, 9 หน้า | 0.08 s | 13.3 MB | 27.7 KB |
| 3,000 แถว, 120 กลุ่ม, 81 หน้า | 0.74 s | 23.1 MB | 205 KB |

ตัวเลขนี้ใช้เฉพาะเปรียบเทียบเวอร์ชันของเราเอง ห้ามอ้างเทียบ Jasper

## 5. ข้อจำกัดที่รู้แล้ว (ค้างไว้)

- **กลุ่มต้องเรียงข้อมูลมาก่อน** — แถวที่ค่าเหมือนกันติดกันคือกลุ่มเดียวกัน ไม่เรียงให้เอง (เหมือน Jasper)
- **ตารางใน band ที่จัดกลุ่ม** — engine คืน error ชัดเจน (ยังไม่รองรับ) ใช้ข้อความวางเป็นคอลัมน์แทน
- **การรวมค่า** — ทศนิยมตายตัว 28 หลัก (`rust_decimal`) ผลรวมเกิน ~7.9×10²⁸ จะเว้นว่าง
- **sources** — มีแค่ SQLite; Postgres/MySQL ต้องเพิ่ม feature ของ sqlx และทดสอบกับฐานจริง
- **HTTP API** — มี timeout และคิวงานแล้ว แต่ยังไม่มี auth และ rate limit ต่อผู้ใช้ ต้องวางหลัง reverse proxy
- **Docker** — ยังไม่ได้ build และยังไม่ได้ทดสอบ container
- **designer** — กลุ่มแสดงผลบนกระดาษออกแบบเป็น band ปกติ ผลจริง (การแบ่งกลุ่ม/ยอดรวม) ดูที่แท็บพรีวิว PDF
